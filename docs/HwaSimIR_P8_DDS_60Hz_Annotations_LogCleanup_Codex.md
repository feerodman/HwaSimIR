## 1. 先清理生成日志，不能先再堆一轮大文件

### 1.1 清理范围

唯一允许删除的根目录是：

`D:\HwaSimIR\logs`

先确认这是普通目录，并检查其规范化路径和实际所在卷。
不操作源码、`.git`、`releases`、生产 `Bin/Config`、安装软件目录、许可证、私钥或板卡 `.before_*` 回滚快照。
不跟随 Windows 目录联接、符号链接或其他重解析点；遇到它们跳过并记录。
不得把用户名、环境变量或空字符串拼成无边界的递归删除命令。

用户授权本轮实际删除安全范围内的历史生成文件，不需要对每个明确候选反复询问。无法判断是否是唯一数据/用户输入的项跳过，列入待确认清单。

### 1.2 不逐个读取历史日志

只枚举目录名、文件名、类型、大小、修改时间，汇总最大的一级/二级目录。

不要向模型发送数万行文件列表，不全文搜索所有日志，不为删除候选逐个解码视频或计算大文件哈希。

## 2. 固定 DDS 主线，澄清 TCP 日志

三程序按正式默认 DDS 启动：
DataDrivenTestQT → DDS → HwaSim_IR → DDS H.264/元数据/诊断 → VideoDisplay。

本轮不运行旧业务 UDP+TCP 回归，不删除旧兼容代码。
确认旧 UDP ingress、TCP Packet v3输出保持关闭；不得自动回退旧链后称 DDS 通过。

现有 QoS 中 `tcpv4://default//0` 是 DDS 自身的底层传输。

不能为了“只测DDS”关闭 DDS 所用 TCP 或无依据改为别的传输。
报告始终区分：
- 旧业务 UDP/TCP：本轮不测；
- DDS 内部传输：仍要排查其重连/发送失败。

保持现有用户协议结构、V1含义、生产SEI版本和录制关联功能；必要的通用诊断扩展要独立版本化，不能占用旧字段改意义。

## 3. 建一个最短的性能原因矩阵

先记录板端当前运行ELF/Config、Windows两程序版本和活动进程。
用正常尺寸800×800、60Hz输入、正常世界双云、同一确定性场景输入，不改变相机或把云移出画面。

先做两个基线：无降水的普通双云、当前NVG雨/当前MWIR雪。
每组预热5秒，统计至少60秒。最终记录全会话计数；测量窗与停止后的排空耗时分开。

优先A/B，避免穷举：
- 同场景，录像开／关：关录像只用于定位，最终必须开。
- 同场景，UI数据刷新正常／临时停止：视频接收和解码保留，避免把“无消费者”当同一场景。
- 同场景，雨雪192／0：0只用于隔离降水增量，最终不能交付无雨雪。
- 同场景，当前性能策略／受控高性能策略。

每组计量：
- 输入实际发送、板端有效接受、执行、捕获、编码、DDS提交、接收、解码、保存计数。
- 同一来源帧各阶段本机单调时间：排队、执行/绘制、读取、颜色转换、编码、SEI/JSON/复制、DDS提交、接收器处理和磁盘写入。
- 每个线程/队列的深度、最老待处理项年龄、峰值、停止排空耗时。
- CPU/GPU/DMC策略与实际可读频率、温度、内存/磁盘、SDK重连事件。
- 本机阶段avg/P95/P99/max，避免只有一项平均renderMs。
- 跨机延时有效样本数、覆盖率、不确定度、P99/max与超80ms数量。

输出与绘制并行，不相加各线程均值当总帧时。
接口请求60、MP4标签60、GUI刷新60都不能代替实际新图60。
P7已经有正确NEON和输出线程CPU4–7设置，核实生效；不重复移植或回退为慢标量实现。
仅对A/B证明的主要项做缓存、减少复制/重复序列化、批量文件写入、复用UI对象等最小修改；不删除正文、SEI或录像来换帧率。

## 4. 允许提高正常板卡性能策略

用户允许本轮提高运行性能；不必再次穷举全体“最低功耗组合”。

P7仓库配置仅供核对，实机以可用频点和驱动能力为准：
- A55：当前最低1200MHz、上限1704MHz；
- A76两簇：当前最低1416MHz、上限2016MHz；
- GPU：当前最低300MHz、上限1000MHz；
- DMC/DDR：当前最低1068MHz、上限2112MHz。

先查实际CPU policy、GPU/DMC devfreq设备、可用频率和governor，确认单位CPU=kHz、GPU/DMC=Hz，不能混写。
高性能候选只在现有受支持上限内提高最低频率或选可用performance策略。DMC没有该governor时使用驱动支持的频率限制，不写不存在的项。

**不超频、不改电压、不刷驱动/设备树、不提高硬件支持上限，不关闭温控和保护。**
保留可恢复原策略、启动读回确认以及串行退出，避免前一个启动器恢复策略覆盖后一个。
不为了“设置成功”吞掉不一致，也不把目标请求频率当实际工作频率。
记录CPU/GPU/DMC分别的变化；不能只调CPU而忽略已经证明重要的内存控制器。

当前策略与受控高性能先各测同一60秒用例。
若高性能有效，再按需定位CPU/GPU/DMC中关键部分，不做几十组无关扫频。
最终候选两波段雨雪各10分钟，并检查温度、频率变化、队列与错误。
温度超过板卡已有告警限或触发保护时终止该候选，不能解除保护继续通过。

通过后把策略写进正式`RK3588PerformancePolicy.conf`和统一启动流程，退出恢复策略保持明确。
不依赖现场人员手动echo或临时环境变量。

## 5. 雨雪按实际预算优化

当前`PrecipitationMaxParticles=192`，一个批次，近场透明图元仍可能有高像素重叠。
在同一板卡策略、相机、天气与显示下测试：
192（基线）→128→96；确有需要再测64。
这些数仅为候选，不是未经测试的最终默认。

必须确认实际提交图元数、采样/覆盖工作随上限下降，不能只改INI而固定绘制192个透明图元。
优先：
- 保持预分配与批量绘制；
- 去除不可见/近零透明度图元；
- 控制近镜头过大雪片和屏幕像素覆盖；
- 远处降水减少密集重叠，边界淡入淡出；
- 避免每帧创建节点/纹理、重复状态设置；
- 保持仿真时间、风、降水高度上限与过渡正确。

减少数量后不能反过来大幅放大单个雪片来凑效果，避免仍然覆盖大量像素。
不改变800×800源分辨率，不退回单云，不降激励到30Hz，不删注释数据或录像。
当前两波段、公共显示、物理模型默认保持；美术参数只作用于普通雨雪表现，不改变对象温度、材料或探测参数。

雨与雪可以采用各自验证过的预算，沿用现有Weather配置体系，不堆临时环境开关。
对最终候选保存同显示/同输入短片，验证雨线/雪片确实在运动且可见。
P7固定gain=1细雨弱对比与正常Auto可见是两个不同结果；不降低图像判据或混用显示设置取消已有失败。
两朵云继续真实贡献像素；光有visible=2日志不够。
近云偏软本轮不靠加体积积分步数解决，四云不扩展。

## 6. DDS 上游少182条输入，单独作为可靠性故障

P7失败轮：发送计数3601，板端接受3419，差182。
`sourceSeq`是板端接受后编号，连续只表示已接受队列连续，不证明网络之前没有缺失。
DDS write成功或ACK成功不等于应用已消费全部数据。

用已有SEI身份、会话/INIT代次和守恒脚本核验：
发送成功计数 → 板端接受 → 有序消费 → 发布 → 接收 → 保存。
同步一一对应；异步的输入数与视频数可以不同，视频与标注仍需正确关联。

需要定位具体输入时，用独立诊断侧记录现有真实字段的稳定摘要与顺序、多重次数，不把本地接收计数冒充发端线序号，不把仿真time或保留字段改作新序号。
有相同输入时按序列/多重性处理，不能只比较摘要集合。

对重连时间附近，查看发送返回值/耗时、reader/writer状态、队列和应用接收事件，查清：
- 是否可复现；
- 是SDK连接恢复、应用退出/STOP时机、线程饥饿还是其他已证实原因；
- 负载恢复后是否还会发生。

本轮不要为了测试变绿改为BEST_EFFORT、Latest或小history丢旧样本。
不要无依据重写listener，也不要阻塞DDS回调执行Panda场景或磁盘重活。
不实现没有发端唯一身份保障的盲目重发，避免重复执行/混合回合。
正常长测要求无非预期重连、无上游数量缺失。
有意断链的异常测试独立命名，明确丢失/恢复区间；不要求网络断开期间也宣称零丢。
无法在当前SDK约束内保证时，报告实际限制，不修改计数或静默补假帧。

## 7. 标注复核：分清保存关联与内容语义

### 7.1 保留P7已经完成的文件检查

直接复用`p7_validate_recording.py`：
真实MP4访问单元/SEI → 产品身份 → 标注正文与哈希 → 索引/PTS → 全帧可解码。
不要恢复到“几个Topic消息数相同就PASS”。

校验器必要时改为流式哈希和有界读取，避免整部视频read_bytes造成内存峰值；先保留原语义与独立参考。

### 7.2 回答用户“框、关重位置、类型是否正确”的边界

现有脚本证明正文保存未串帧，不等于证明正文内几何与模型语义正确。
只读核查现有输出字段，并把结论分成：
- 保存关联已验证；
- 格式、坐标约定与枚举传递已验证；
- 普通几何投影测试已验证；
- 业务模型关键位置语义未标定。

不新增/修订真实装备关键部位定义、位置参数，不优化目标定位或打击用途。
普通几何体的已知矩形/人工标记点用于检查通用坐标、翻转和显示问题。

### 7.3 通用格式与显示检查

读取实际schema，不凭猜测创造字段。
对每帧现有正文检查：
- 原始width/height、帧身份、来源输入身份、实例/通道/代次；
- 数值有限，字段类型正确，类型码与当前输入/显示枚举映射一致；
- 多对象ID不串，目标数按实际有效数量，不把UI预留空行当对象；
- 框是xywh还是xyxy，坐标是源像素还是归一化，原点在哪里；
- 对声明为有效的框/点应用明确范围检查；
- 不在画面/被遮挡/无效点应有明确状态，不能用(0,0)伪装有效；
- 原始框与裁剪框若均存在分别命名，不把图外框一律判坏；
- 保存800×800，UI最大1024显示只作一次尺度与留边变换；
- 垂直翻转只按正确阶段处理一次。

独立普通场景测试：静止矩形、已知移动标记、进出画面、两物体遮挡、1/2/5普通对象、暂停、两次INIT、UI缩放。
预期点/框来自独立简单解析输入或独立测试图定义，不从被测标注反过来生成“真值”。
保留每帧检查CSV及选帧图；若发现传输/保存/翻转错误做最小修复，不改业务模型语义。

结果不能写成“所有模型关重位置已准确标定”。没有依据时明确“当前只证明该字段被完整传递和保存”。

## 8. 其余P7未完成项

### 延时
继续保留时基可靠性、有效覆盖率、≈号和未测状态。
核查MWIR雪30Hz最大约204ms发生在什么时刻，有无可靠估计、队列变化、写盘/GUI或初始化事件。
不能只保留P99并删除真实尖峰。
“板端应用接受→Windows完整AU到达”不包含板端接受前的DDS等待，报告另列发端/接收差值，不能把这个时延当所有上游等待都已覆盖。

若技术要求是每帧不超过80ms，有效最大值超过即该项失败，P99<80不能替代。
尚无可置信估计的场景保持未测；估计误差与实测不足不得写成严格硬实时证明。

### 4K
有真实3840×2160显示器再做实屏与DPI切换测试。
没有实屏时完成3840×2160逻辑布局/虚拟屏自动检查并标“模拟布局”，4K实屏仍标未测。
保留1080p/2K已通过布局、左右各半、平台2行/目标7行与视频物理像素上限。
不得放大旧截图冒充4K测试。

### 云和游戏画面
仅修复与本轮雨雪预算直接相关的过度遮挡、过粗雨线、大雪片填屏等通用外观问题。
不再提高尾焰或对象物理亮度以补偿显示，不扩展真实特征拟合。
近云偏软、完整体积遮挡/地形阴影、真实器件标定若不在本轮范围，逐项保留边界。
不要写“全部剩余问题均已解决”覆盖这些未完成项。

## 9. 最终验收门槛

最终从普通Windows发布包与板端`./run_precise.sh`启动，无临时transport/诊断覆盖。
所有统计使用实际执行并生效的设置，声明源码和完整配置身份。

顺序：
1. 所选策略下普通双云60秒基线；
2. NVG雨、MWIR雪各60秒；
3. 1～2全部满足后，两者各10分钟；不要明知仅49FPS仍重复完整长测当通过；
4. 同步20/30Hz短回归、暂停、两次INIT；
5. 异步输入/输出独立的短回归，保持videoFps=0语义；
6. 最终录像全帧核验和通用标注测试，在性能计时结束后运行。

最终60Hz同步组要求：
- 请求并实际发送约60Hz；每条有效输入仅生成对应视频，不补帧、不合并；
- 稳态实际接收约60FPS（至少59.5FPS作为工程采样下限，不降低协议要求），同时数量/顺序完整；
- 发端成功输入与板端接受、有序消费、捕获/视频、接收/保存对应；
- 不发生上游缺失、旧帧、重复、覆盖、溢出、正文错配或错误解码；
- 队列可以短时因批到达增长，但不长期满16、无持续增长，尾部排空时长受控；
- 正常长测满队列回压为0；若偶发出现，单列时间与排队年龄，不能直接写严格零积压通过；
- 录像和真实数据页同时开启，实际800×800，两朵云与雨雪均可见；
- 温度、实际可读频率、SDK事件、内存和磁盘稳定；
- 输出延时按有效样本分别报告，不用帧率替代延时。

达不到时不要降成30Hz宣称恢复；记录最佳候选、实际通过范围与明确阻塞项，保留可以恢复的稳定版本。
原P7 30Hz配置只作为已知可用临时方案，不改写为正式60Hz成果。
