## 2. 四项界面统计必须有真实来源

数据显示半区顶部新增“运行监测”区，2×2 排列，主标签按用户要求：

- 视频实时帧率（FPS）
- 数据接收频率（Hz）
- 指令处理频率（Hz）
- 输出延时（ms）

其下可放小字：当前模式、请求视频帧率、实际源图尺寸、统计状态。不要把请求 60 Hz 当成实测。

### 2.1 频率定义

使用单调时钟，真实统计窗长度，频率 = 窗内事件数 / 窗口秒数。主界面最近约 1 秒滑动窗，每 250 ms 更新文字；频率统计与界面刷新频率不是一回事。

1. 视频实时帧率：接收端实际成功解码并提交新视频图像的频率；不计 UI 重绘旧图、元数据到达或计时器回调。记录解码与呈现计数，不能合并成不明口径。
2. 数据接收频率：HwaSim_IR 应用层收到并校验/路由为本实例的有效实时激励样本频率。位置在应用有序队列之前。不是发送端计划 Hz，也不是 VideoDisplay 自己订阅相同 Topic 得到的 Hz。
3. 指令处理频率：本轮按“每秒从队列取出并开始执行的有效实时指令数”统计。提示文字写明该定义；RESET/INIT/START/STOP 单独计数，不混入稳定实时 Hz。该频率不能用 `1000 / 平均排队耗时` 推导。
4. 另在详情/日志保留“接收→开始执行等待（ms）”，用于直接解释队列延迟，它不是频率。

UI 表格刷新可降到 5–10 Hz 并合并过时的纯 UI 更新；接收、逐帧产品、编码、录像、标注与真实视频计数不得因此丢失。

停止、断连、未初始化要区别显示：已停止且有效统计窗空时为 0；缺来源或过期显示 `— / 未连接`，不是沿用最后一个 60。

### 2.2 输出延时的起止点和时钟限制

用户定义的主要输出延时：

`t_receive_video_at_display - t_receive_realtime_at_HwaSimIR`

起点为板端 DDS 应用回调取得并接受该完整实时样本的入口，终点为 VideoDisplay 应用层收到对应完整视频访问单元的时刻（解码前）。明确：这不是网卡收到首字节，也不包括无法测定的 DDS 回调前内部等待。

分别记录同一产品的：板端接收、开始执行、成功捕获、编码完成、真实 DDS writer 提交/返回、接收端视频到达、解码完成、GUI 新图提交。不要用本地入发送队列的耗时冒充网络发送完毕。

两机当前未对时，禁止直接相减墙钟或无关联的 steady_clock/QElapsedTimer 值，禁止使用协议仿真 `time`/`ptsMs` 冒充真实时刻，禁止把负值裁为 0 后宣布低延时。

实现不修改系统时间的可选应用层时基关联：

- 用独立低频诊断请求/响应交换两端发送、接收时刻，记录进程/启动时基身份；使用自身明确定义的单调基准，而非假设两机计时器同源。
- 估计两端时基偏差，优先采用较低往返时延样本；维护漂移/有效期和网络不对称带来的不确定度。
- 重启、断连、时基异常、校准过期后失效，重新建立。
- UI 清楚显示 `≈数值（估计）`；详情显示误差估计、有效样本数、统计起止点。未经校准则 `—（未建立时间基准）`。
- 板端“接收→提交输出”可准确用本机时钟计算，但只可作为另外一项局部耗时，不得顶替用户要求的全链路延时。
- 不要求用户先改系统时钟。不因暂时缺少可靠全链路时基就停止其它界面和录像任务。

可借鉴四时间戳的偏差/往返时延定义，但不能把应用层估计宣称硬件级时钟同步。只有数值加不确定度也能支持时，才评价是否满足原 80 ms 要求。

### 2.3 传输统计的兼容方案

先复用确实存在且语义明确的诊断承载。若现有消息不能承载，新增独立、版本化 DDS 诊断消息/Topic（可复用已有 Bytes/String 类型和同一 RuntimeManager），承载统计和时基关联。

- 不改 CommonData 及既有 V1 IDL 字段含义、Topic 或 H.264 Annex-B 业务帧格式。
- 不把新含义塞进旧 `ptsMs`、`time`、fps、flag 等字段。
- 诊断缺失不影响视频；旧客户端继续可用。
- 常规汇总低频发送，逐帧时刻与帧身份使用明确的轻量产品记录；不用读终端日志当 UI 接口。
- 按实例身份、通道、会话/初始化代次区分；一次 Init 不重建整个 DDS runtime。

## 3. HwaSim_IR_VideoDisplay 界面精确要求

### 3.1 左右固定一半

保留现有蓝绿/绿色整体风格，但降低装饰边框对空间的占用。

可用客户区扣除统一外边距/间隙后：左侧数据 50%，右侧视频 50%，相差最多 1 个逻辑像素。取消原固定 480 侧栏、可拖动比例和标签页分隔。可用 QHBoxLayout 对称 stretch 或受控等分布局实现，不靠固定坐标摆放。

左侧一页从上到下：

1. 运行监测四指标；
2. 场景/环境参数；
3. 传感器探测成像参数；
4. 平台运动数据；
5. 目标运动数据。

场景、平台、目标全部同页。正常要求范围内不靠滚动、标签切换或展开操作才能读数据。

### 3.2 表格和参数区

- 平台预留 2 行（常用 1 行 + 1 空行），不要让它独占半屏。
- 目标预留 7 行（最多 5 条有效记录 + 2 空行）。空行仅供布局，不伪造目标。按真实有效数量填充，不能遇到空槽就误判后面都无数据。
- 当前列全部显示，平台/目标表不出现横向、纵向滚动条，也不以省略号或裁掉单元格代替。
- 使用真实可用宽度和字体度量分列；表头可两行，单位写在表头；保留经纬度/角度等既有合理显示精度，底层值不变。
- 传感器和环境参数采用多列 label/value 网格，每行尽可能 3–4 对，空间不足时受控重排；不是每项占整个屏幕一行。
- 控制表格高度为 header + 2/7 行 + 边框；不要伸缩成巨大空白表。
- UI 复用已有 item/model，不逐帧 setRowCount(0) 再整表创建对象；保证数据始终使用线程安全快照。

删除显示项：“是否开启精跟”“是否开启粗跟”“精角分辨率”“粗角分辨率”。只删除过时 UI，不改当前有效协议。

在传感器显示区域新增：

- `trackingInit.simMode`：1 显示“同步”，2 显示“异步”，其它显示未知数值。
- `trackingInit.videoFps`：0 显示“不限帧”，正值显示“xx FPS”。

这两个成员实际属于 trackingInit，不在 trackerSensorParam，不要为了 UI 移动结构成员。同步模式仍以有效输入为准；videoFps 作为异步输出目标，不得强迫同步20Hz输出60Hz。

### 3.3 视频区域

- 视频在右半区居中，保持实际图像宽高比，不裁剪、不拉伸。
- 显示边界上限为 1024×1024 屏幕物理像素；空间不足时继续缩小。800×800 原图可仅在显示上放大，但不改变编码和保存分辨率。
- 根据当前 devicePixelRatio 把屏幕像素上限转换成 Qt 逻辑尺寸；同时记录两种尺寸防止4K/200%下误放大至2048。
- 1080p 左右各半时右边通常不足1024宽，不能强行塞进1024；取可用区域与上限的较小值。
- 不把整个右半区大小强制为1024；只有视频图像矩形受限，周围允许留白。

### 3.4 分辨率和高 DPI 验收

Qt 保持当前已安装版本（Qt 5.12 系列实际构建为准），不调用仅5.14/Qt6存在的高DPI API，不升级SDK来规避布局问题。

测试客户区最大化及真实全屏：1920×1080、2560×1440（本任务按2K/QHD）、3840×2160。主要缩放矩阵：1080p 100%/125%，2K 100%/150%，4K 150%/200%；再尽可能覆盖100%。截图记录实际物理分辨率、客户区逻辑大小、DPI和DPR，不能把缩小的截图冒充4K实测。

验证 1 条平台和 5 条目标的所有文本可见。较窄逻辑面积先减少空白、改多行表头/紧凑记录布局，不用无限缩小字体或隐藏字段通过。极端缩放造成客观空间不足时单列实际边界，不宣称所有分辨率和任意缩放均通过。

界面显示0 FPS且发送器已停止时是正常闲置状态，不单凭静态截图判定冻结。

在相邻初始化区域增加 simMode 与 videoFps。其它 trackingInit 天气字段保持真实现有来源，必要时显示环境选择，便于雨雪回归；不让无关默认重置用户配置。

### 4.2 防止表单改了却没发出去

- 用一个表单数据对象构造真实 Init 命令；去掉后续硬编码800×800等覆盖。
- 用户显式修改、命令行自动化、保存配置采用一致构造路径，明确优先级；不保留两套相互漂移的初始化实现。
- 用非默认值逐字段回读测试，验证发送前、DDS roundtrip及接收端显示一致。
- 保留旧字段宽度和协议布局；当前基线尺寸按构建测得并与既有24/385/506/17记录核对，不增删旧协议字段。
- 运行中编辑不悄悄影响当前回合；停止后修改、下一次INIT生效，或清楚标记“下次初始化生效”。
- 可以保存/读取独立本地初始化配置，但不把客户机器网络或许可证数据写入公开文件。

### 4.3 清理实时配置区并分离发送步长

删除旧“实时成像数据配置”中失去意义/被文件覆盖的可编辑目标类型、FOV、重复FPS、平台/目标姿态和速度等项；该区只保留“发送步长（ms）”。

既有激励文件入口、平台/传感器身份和合法目标选择需要的值保留真实数据来源。若旧输入仍被某处消费，先迁移到对应初始化/数据源区再删除控件，不能留下空指针或默认0改变行为。

发送步长表示输入间隔；videoFps表示异步输出目标，二者完全独立。允许小数步长和绝对deadline调度；16.666667ms对应约60Hz，不强制四舍五入为17ms。videoFps=0必须合法且不参与除零运算。

回归：同步输入20/30/60Hz；异步输入30Hz而视频60FPS；异步videoFps=0明确不限帧。不要删除旧命令行自动化入口。

“UDP通信配置”根据当前传输方式显示为“DDS通信配置/通信配置”；纯DDS下原UDP地址不得伪装正在控制DDS。旧UDP参数可在兼容配置下保留，默认不启动旧业务链。

## 5. 保存的视频和标注必须逐帧核验

### 5.1 先定位所有保存端

列出板端录像、Windows录像、标注JSON/文本及图像帧保存的实际路径、开关、写入者。检查saveMP4En/realtimeAnnotation分别影响什么；不存在的保存路径如实标记，不虚构文件。

不能只检查“三种消息数量相同”。尤其修正processAnnotation丢弃正文、processVideoMeta丢弃PTS、视频使用本地计数身份带来的证据缺口。

### 5.2 通用 FrameProduct 关联

统一使用不可变的每帧产品快照：实例身份、通道、会话/初始化代次、回合、真实输出frameSeq、来源sourceSeq（如可获取）、真实PTS、图像/码流、标注正文和有效状态。

- 每次INIT都是新代次，即使currentRound仍为1；相同回合号不能延续旧集合。
- 按生产方帧身份配对，不按回调到达先后或“最近一次标注”。
- 现有视频Bytes若不带生产帧身份，不能仅给本地自增变量改名声称解决。先验证目前可靠、有序、从回合起点订阅的限制；对晚订阅、重连、丢一个样本的情况实测。
- 如需新增身份承载，采用保持旧V1类型和普通H264解码兼容的独立版本产品描述或兼容媒体元数据；先写清方案及旧端兼容。不得破坏现有1访问单元/1DDS视频样本。
- 无法确认配对时明确unmatched，不伪造标注、不以空JSON充数、不静默重复上一帧。
- 实时显示可选择不被短暂标注延迟阻塞；保存链必须按准确身份写出或明确记录不完整产品。
- 有界缓存，正常消费后清理；不能无限增长集合或每秒遍历整个十分钟历史。
- 原始图像坐标、裁剪/翻转和保存尺寸保持一致。UI缩放到1024不改保存标注坐标。

### 5.3 实际保存文件测试

用带可识别帧号的普通移动几何/测试图，记录独立的预期位置，不增加业务目标能力。

测试0、1、5个记录，进入/离开画面、遮挡、标注开关、同步20/30/60Hz、异步重复状态、暂停、两次同回合号INIT、接收器重启/晚加入，以及模拟不同Topic延迟。

真正打开最终保存MP4或图像序列与标注文件，逐帧核对：解码帧索引、PTS、sourceSeq、frameSeq、轮次/代次、标注数量、格式和普通测试几何坐标。输入日志与文件索引共同验证，不能用绘制出的标注本身作为唯一预期真值。

尽量保持已有格式，新增可选索引侧车 `frame_index.jsonl` 明确每个存储帧与正文对应关系。只在用户开启保存时生产保存；验收将文件保留在独立目录。

交付全量 `annotation_frame_alignment.csv/json`、实际视频与标注文件、固定选帧对照、异常场景结果和哈希。关闭功能导致缺标注写“按配置关闭”，不是通过或故障混称。

## 6. 已有主动照明的通用回归

本轮不新增跟踪、探测或真实目标特征功能。只使用普通平板/球体，沿用已有控制字段和功能实现，验证：

不按现实设备照片或武器工况调参。保存输入、有效配置、相同普通场景前后帧、日志及结果CSV。若现有接口回归有缺陷，只修普通开关/状态生命周期/配置消费错误；超出本轮范围的物理或业务能力问题单列。

## 7. NVG 排队与穿云 Auto 的最小收口

新增雨雪前先得到基线，避免在持续排队上叠加透明特效。

同一普通云场景分别用固定显示/冻结Auto/动态Auto、录制开关、旧/新UI做隔离；分开统计板端处理、输出线程、DDS中间件与GUI事件队列，不根据接收GUI FPS直接判断GPU不足。

必须记录实际计时范围：do_frame之外的捕获、队列等待、编码、GUI耗时不能漏掉；输出与渲染线程并行不能机械相加。

只优化A/B证明的项，优先清除不必要每帧分配、锁等待、UI表格重建、反复扫描历史集合和统计/录像额外同步。不能恢复Latest、扩大FIFO掩盖延迟、跳帧、降低源分辨率或永久关闭Auto/双云来写通过。

穿云明暗突变用同一路径固定显示/动态映射分离。允许在现有公共Auto中增加按仿真经过时间连续变化、低对比阈值滞回和安全限幅，避免阈值分支突然跳转；不要全局亮度补丁或整幅时间拖影。暂停、INIT、不同输入频率要验证。

最终标明真实队列等待次数、累计/最大等待、稳定队列分布、恢复时间。累计回调等待不是单帧延时，但长期接近测试时长是实时性未通过。必须分析，不能只写“最后排空”。

## 8. 云团避免过圆的游戏外观修订

用户认为云像人工圆团，是需要复验的外观问题，不预设所有圆形都错误。先保存多模板、多视角、固定映射图。

优先离线改派生密度：非对称主团、不同尺度的附属团、疏密过渡、局部孔隙和边缘破碎度。避免所有小团半径接近、等距排列，或统一球形包络形成整齐轮廓。既有原图alpha可继续作形态参考，但不能再次挤出PNG人工灰纹。

保持R密度/G人工明暗职责、P6D已验证的source-over、零密度等价和世界身份。固定种子与显式模板清单继续有效。世界位置不变，外观缓存改变要更新资源哈希与派生版本，两个实例同步部署。

尽量不增加96³体大小、双云预算与每帧采样次数；先改离线形态，避免重新引入条带、黑带、挖空接缝和性能退化。不用整体模糊或全部抬白换“自然”。

## 9. 游戏发光特效稍大、稍亮

只做不按现实设备标定的外观倍率，不改物理温度、材料、发动机响应、亮斑或辐射功率。优先在普通喷口样例里验证，保持已有挂点与发射方向。

在GameVFX现有结构内明确宽度、长度、公共线性外观亮度/不透明度倍率，分别A/B；默认1.0可恢复。先做小范围候选，不把全画面白饱和当成功；不新增大量粒子或对象。

交付旧值/新值/生效位置与端面、侧面、斜角、近远、普通遮挡图。亮核、主体和烟气仍分层，不能再次变回X型交叉片。阴影/黑热显示分别标注。

未取得外观确认前保留可恢复旧预设；不能改变整个场景显示Gain以增亮这一项。

## 10. 雨、雪：简单、有空间感、不牺牲帧率

使用已有 `Config/Weather/Textures` 素材，先检查实际文件头、通道和加载能力：`rain_shaft.png`、`rain.rgba`、`snow.rgba`。不要把扩展名.rgba直接当裸字节RGBA；如需兼容派生PNG，由工具离线生成并纳入清单，原文件保留。

优先复用已有天气效果/批量精灵：小范围近景深度分层的雨线与雪片，带风向、透视大小、淡入/淡出和实际仿真时间动画。对象池/图集预分配，批量绘制，不每粒子一个节点，不逐帧读文件。

- 晴/云等非雨雪配置不残留降水。
- 下雨呈方向一致的细雨线及疏密层次；下雪速度和大小有稳定变化，不只是把雨线放慢。
- 原生深度可遮挡普通物体，透明层不写深度。不要为了雨雪恢复已失败的深度纹理反馈路径。
- 使用现有envSky=2/3及最大降水高度、过渡高度、相对速度、风等字段；先确认参考高度与代码定义，不把局部Z误当海拔。
- 不在远高于降水层的镜头前强塞雨雪。验收选择确实处于有效降水范围的普通相机；另测越过高度阈值后平滑消失。
- NIR/MWIR复用各自明确显示口径；雨雪素材是外观遮罩，不能宣称实测光谱或强迫所有雪片自发白光。
- 保持画面可读，避免全屏遮白；透明覆盖面积与数量同时限预算。
- 双云+雨、双云+雪分别测试，不用降成单云或关闭标注录像写通过。

先验证既有实现能否只补配置和少量代码完成，不重建完整天气系统。
